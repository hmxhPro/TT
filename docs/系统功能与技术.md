# 系统功能与技术

> 本文档介绍系统的**功能、架构与技术实现**。如何安装、配置、启动与迁移见根目录 [`README.md`](../README.md)（部署文档）。

基于 **FastAPI + YOLOE + ByteTrack + React** 的视频目标检测系统：用户上传视频、用**自然语言**描述要检测的目标，系统逐帧检测、持久跟踪，并通过 SSE 把结果实时回传前端。

## 核心功能

- **自然语言开放词汇检测**：输入中文名词（如"菜地、水塘、钓鱼台"），无需预训练类别即可检测。
- **持久多目标跟踪**：ByteTrack 为每个目标分配稳定 `track_id`，跨帧不漂移。
- **每 N 帧全量检测 + 中间帧 Kalman 预测**，吞吐较逐帧检测提升约 **4~8×**。
- **VLM 语义复核**：检测得分与大模型得分按 `0.4 / 0.6` 加权融合，驱动 `tentative → confirmed / rejected` 状态机，显著降低小目标 / 罕见类误检。
- **自定义模型训练**：网页端"建类别 → 上传 → 框选标注 → 一键训练 YOLOE"，或命令行训练；产物权重可直接接回后端。
- **实时结果流 + 结果归档**：SSE 逐帧推送；任务完成打包 ZIP（标注帧 + `results.json` / `results.csv`）。
- **任务历史持久化**：PostgreSQL 落库；数据库不可用时自动降级为内存模式，不影响检测主路径。
- **多页面控制台前端**：概览 / 视频检测 / 模型训练 / 历史记录四个页面，左侧栏导航，支持**深 / 浅色主题切换**；检测任务在页面间切换时保持实时流不中断。

## 技术方案

| 层次 | 技术选型 | 说明 |
|------|---------|------|
| 后端框架 | **FastAPI** | 异步高性能，原生支持 SSE / WebSocket |
| 主检测模型 | **YOLOE**（Ultralytics） | 开放词汇 YOLO，速度快、显存低，**支持自定义训练** |
| 备选模型 | **YOLO-World** / **Grounding DINO** / **Florence-2** | 同样支持开放词汇检测，可按需切换 |
| 小目标增强 | **SAHI** | 大图自动切片推理，显著提升小目标召回 |
| **大模型 (VLM)** | **MiniCPM-V**（默认）/ 任意 OpenAI 兼容模型 | **Prompt 标准化 + 检测结果语义复核**，支持本地 vLLM 与远端 API |
| 目标跟踪 | **ByteTrack** | 无需重检测的多目标跟踪，大幅降低 GPU 开销 |
| 实时推送 | **Server-Sent Events (SSE)** | 逐帧推送，前端实时刷新 |
| **任务持久化** | **PostgreSQL + SQLAlchemy 2.x (async / asyncpg)** | 历史任务、状态、进度落库；DB 不可用时降级为内存模式 |
| 前端 | **React 18 + Vite + Tailwind CSS + react-router** | 多页面控制台，HashRouter 路由，CSS 变量主题系统 |
| 部署环境 | Linux + NVIDIA GPU (CUDA) | 推荐 RTX 3090 / A100 或更高 |

> 默认检测后端为 **YOLOE**（`yoloe-11l-seg.pt`），在 `backend/.env` 的 `DETECTION_MODEL` / `YOLO_WORLD_MODEL` 中切换。大模型默认指向本地 vLLM（`http://localhost:8010/v1`，MiniCPM-V），改 `VLM_API_BASE` / `VLM_MODEL_NAME` 即可切到远端 API。配置细节见 [README](../README.md)。

### 检测 + 跟踪流程

```
视频帧序列
    │
    ├── 每隔 N 帧（默认 N=5）→ YOLOE 全量检测（GPU，可选 SAHI 切片）
    │                           ↓
    │                        ByteTrack.update(detections)  ← 分配持久 track_id
    │                           ↓
    │            （可选）VLM 语义复核：对低/中置信度 track 把裁剪图发给大模型
    │                              判断是否真为目标，与检测得分融合
    │
    └── 其余帧 → ByteTrack.update(last_detections)  ← Kalman 预测（纯 CPU）
                    ↓
              画框 + 保存 + SSE 推送
```

该策略带来约 **4~8×** 的吞吐提升（取决于 N 值与模型大小）。

## 大模型 (VLM) 工作原理

系统集成一个**视觉-语言大模型（VLM）**，服务于两个用途（部署与配置见 [README](../README.md#大模型-vlm-配置)）：

1. **Prompt 标准化**（`app/services/prompt_normalizer.py`）：把用户的中文自然语言（如 `"菜地、水塘"`）转换成检测器友好的英文短语（如 `"vegetable field. water pond."`），并抽取目标类型（common/small/rare）、颜色过滤规则、视觉特征等元信息，用于后续阈值调整与降权。

2. **检测结果语义复核**（`app/services/vlm_service.py` + `fusion_engine.py`）：对低/中置信度 track，把检测裁剪图发给 VLM 判断"图中是否就是用户想要的目标"，返回得分与检测器得分按 `VLM_WEIGHT` / `DINO_WEIGHT` 加权融合，驱动 `tentative → confirmed / rejected` 状态机，显著降低小目标和罕见类误检。

两个模块统一使用 **OpenAI 兼容的 Chat Completions 协议**（`POST {VLM_API_BASE}/chat/completions`），因此同一份代码既能调本地大模型也能调远端 API。

### 工作时序（简化）

```
检测器输出 box（low/mid confidence）
        │
        ▼
fusion_engine 判断该 track 是否需要复核
        │ 满足间隔条件
        ▼
vlm_service.crop_detection(frame, box)  ← 自适应扩边
        │
        ▼
POST {VLM_API_BASE}/chat/completions     ← 本地 or 远端
   payload: { image_b64, target_text }
        │
        ▼
解析返回 JSON: { is_target, matched_label, confidence, reason }
        │
        ▼
fusion_engine.apply_vlm_result(...)
   final_score = 0.4 * dino_score + 0.6 * vlm_score
   → confirmed / rejected / tentative
```

## 任务历史持久化设计

后端用 **PostgreSQL** 持久化任务元数据与状态，配合 SQLAlchemy 2.x 的 async ORM + `asyncpg` 驱动，全异步、不阻塞流水线。建库与配置见 [README](../README.md#postgresql-建库)。

### 设计要点

- **懒连接 + 启动不崩**：引擎在 import 时创建，连接池首次查询才建立——配置错误或 DB 不可达**不会**阻止后端启动，错误在首次查询时由持久层 `try/except` 捕获，**检测主路径不依赖 DB**。
- **DB 不可用时降级**：历史接口在 DB 失联时返回 `503`，前端仍可上传与检测，只是看不到历史；任务在内存 `task_manager` 中正常调度。
- **磁盘联动**：删除任务时同步清理 `RESULTS_DIR/{task_id}/`（帧 + ZIP）；对上传视频做引用计数，仅当无其它任务引用时才删。
- **活动任务保护**：`pending / running / paused / packaging` 的任务不可删除，必须先取消。
- **二次确认 + 审计**：全量清空需 `confirm=DELETE_ALL`，按行删除（不整目录 wipe），操作写入 `operation_log`。

### 启动时自动创建的表

| 表名 | 用途 |
|---|---|
| `detection_tasks` | 视频检测任务历史（状态 / 进度 / 时间戳） |
| `yoloe_categories` | 训练类别（draft → annotating → ready → trained） |
| `yoloe_dataset_images` | 每个类别下上传的图片 + 标注状态 |
| `yoloe_training_jobs` | 每次训练任务（进度 / 指标 / best.pt 路径 / PID） |
| `yoloe_trained_models` | 已训练模型注册表（供前端模型列表选择） |
| `operation_log` | 危险操作审计（如清空历史） |

#### `detection_tasks` 表结构

| 列 | 类型 | 说明 |
|---|---|---|
| `task_id` | `VARCHAR(36)` PK | 任务 UUID |
| `video_id` | `VARCHAR(36)` | 关联上传视频 ID |
| `video_filename` | `VARCHAR(512)` | 原始文件名（可空） |
| `prompt` | `TEXT` | 用户的自然语言检测目标 |
| `status` | `VARCHAR(32)` *(indexed)* | `pending`/`running`/`paused`/`packaging`/`finished`/`failed`/`cancelled` |
| `progress` | `FLOAT` | 0.0 – 1.0 |
| `total_frames` / `processed_frames` | `INT` | 帧计数 |
| `error` | `TEXT` | 失败原因 |
| `zip_ready` | `BOOL` | ZIP 是否可下载 |
| `early_terminated` / `termination_reason` | `BOOL` / `TEXT` | 是否提前终止及原因 |
| `created_at` *(indexed)* / `updated_at` / `finished_at` | `TIMESTAMPTZ` | 时间戳（带时区） |

> `init_db()` 的 `create_all` **只创建缺失的表，不修改已存在的表**。Schema 演进需接入 Alembic（`pip install alembic` → `alembic init` → 配置 `sqlalchemy.url` 指向 `settings.DATABASE_URL` → `alembic revision --autogenerate` → `alembic upgrade head`）。

## 训练自定义 YOLOE 模型

支持基于自有数据集对 YOLOE 微调或从头训练。两种入口：**网页端工作流**（建类别→上传→框选→一键训练）和**命令行**。命令行完整说明见 [`backend/YOLOWorld/TRAINING.md`](../backend/YOLOWorld/TRAINING.md)，要点如下。

### 1. 准备数据集（YOLO 标准布局）

```
/your/dataset/
├── images/{train,val,test}/   # 图片（test 可选）
└── labels/{train,val,test}/   # 同名 .txt，每行: <class_id> <cx> <cy> <w> <h>（归一化 0–1）
```

### 2. 编写数据集 YAML

```bash
cp backend/YOLOWorld/dataset.yaml.example backend/YOLOWorld/dataset.yaml
```

```yaml
path: /your/dataset          # 数据集根目录（绝对路径）
train: images/train
val: images/val
test: images/test            # 可选
names:
  0: tower
  1: insulator
  2: vegetation
```

### 3. 启动训练

```bash
# 单卡基础训练
python backend/YOLOWorld/train_yoloe.py \
    --data backend/YOLOWorld/dataset.yaml \
    --epochs 100 --imgsz 640 --batch 16 --device cuda:0

# 多卡训练
python backend/YOLOWorld/train_yoloe.py --data backend/YOLOWorld/dataset.yaml --device 0,1 --batch 32

# 断点续训
python backend/YOLOWorld/train_yoloe.py --data backend/YOLOWorld/dataset.yaml --resume

# 冻结主干、轻量微调
python backend/YOLOWorld/train_yoloe.py --data backend/YOLOWorld/dataset.yaml --epochs 30 --freeze 10 --lr0 0.001
```

完整参数：`python backend/YOLOWorld/train_yoloe.py --help`

### 4. 训练产物 → 接回检测后端

```
backend/runs/train/yoloe_exp/weights/
├── best.pt    # 验证集最优权重 ← 部署用这个
└── last.pt    # 最后一轮（用于续训）
```

把 `best.pt` 绝对路径写回 `backend/.env` 的 `YOLO_WORLD_MODEL`，重启后端即可使用，业务代码无需改动。网页端训练完成的模型会自动注册进模型列表供选择。

> ⚠️ mAP50 为 0 / 异常的模型会被标为 `needs_review` 不进入可选列表；当已标注样本过少（val 镜像 train）时，指标会被标注为"训练集自测"，不可作为泛化依据。

## API 接口说明

> FastAPI 在 `http://localhost:8000/docs` 提供交互式 Swagger 文档（权威来源）。以下为常用接口摘要。

### `POST /api/upload`
上传视频（`multipart/form-data`，字段 `file`）。响应：
```json
{ "video_id": "3f4a1b2c-...", "filename": "my_video.mp4", "size_bytes": 52428800,
  "duration_seconds": 30.5, "fps": 30.0, "total_frames": 915 }
```

### `POST /api/detect`
创建检测任务（立即返回，后台异步处理）。请求体：
```json
{ "video_id": "3f4a1b2c-...", "prompt": "帮我检测视频中的菜园", "detection_interval": 5, "enable_vlm": true }
```
响应 `202`：`{ "task_id": "9a8b7c6d-...", "status": "pending", ... }`。`enable_vlm` 覆盖 `.env` 全局设置。

### `GET /api/task/{task_id}`
查询任务状态（轮询备用）：`{ "status": "running", "progress": 0.42, "processed_frames": 385, "total_frames": 915, "zip_ready": false, "results": [...] }`

### `GET /api/stream/{task_id}`
SSE 流，每处理完一帧推一条：
```
data: {"event_type":"frame","frame_result":{...},"progress":0.1,"processed_frames":10,"total_frames":100}
data: {"event_type":"done","progress":1.0,"processed_frames":100,"total_frames":100}
```

### `GET /api/download/{task_id}`
下载 ZIP（任务 `finished` 后可用）：标注帧 JPG + `results.json` + `results.csv`。

### 历史接口

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/tasks?limit=100&offset=0&date=YYYY-MM-DD` | 分页列出历史（`created_at` 倒序，可按日期过滤）；DB 不可达返回 `503` |
| `GET` | `/api/task/{task_id}/frames` | 列出该任务保存的标注帧文件名（无目录返回 `404`） |
| `DELETE` | `/api/task/{task_id}` | 删除单任务：DB 行 + 结果目录 + ZIP + 引用计数后的上传视频（活动中返回 `409`，成功 `204`） |
| `DELETE` | `/api/tasks?confirm=DELETE_ALL` | 二次确认全量清空（缺确认串返回 `409`，有活动任务返回 `409`） |

此外还有训练工作流接口：`/api/categories`、`/api/categories/{id}/images`、`/api/categories/{id}/train`、`/api/training/jobs`、`/api/models`、`/api/image-detect` 等，详见 Swagger。

## 横向扩展

当前设计：单 GPU，通过 `asyncio.Semaphore(MAX_CONCURRENT_TASKS)` 控制并发任务数。规模化可选以下方案。

### 多 GPU：每 GPU 一个 Worker 进程

```bash
DEVICE=cuda:0 uvicorn app.main:app --port 8000 &
DEVICE=cuda:1 uvicorn app.main:app --port 8001 &
```

```nginx
upstream backends { server 127.0.0.1:8000; server 127.0.0.1:8001; }
```

### 提升吞吐

| 优化手段 | 预期收益 |
|---------|---------|
| 增大 `DETECTION_INTERVAL`（5→10） | 推理帧数减半，速度约 2× |
| 用 `Florence-2-base` 代替 `-large` | 速度约 1.5~2×，精度稍降 |
| TensorRT 量化 Grounding DINO | 速度约 2~3× |
| NVDEC 异步解码 | 解码不占 CPU |
| 批量推理（batch > 1） | 对检测帧批量 forward |
| 半精度（fp16）推理 | 速度约 1.5×，显存减半 |
